SOFT DELETE KOD TEKRAR KULLANIMI — 28.10.2026
================================================
Problem ve temel neden:
  Çok sayıdaki standart tanım zaten !IsDeleted iş kuralları ve IsDeleted=false
  kısmî (partial) UNIQUE index ile doğruydu. Ancak tam üç kod tablosu
  (ProcedureTypeDefs, SYYDiagnosisTypeDefs, SYYDiagnosisSliceDefs)
  .HasAlternateKey(Code) nedeniyle IsDeleted=true kayıtları da blokluyordu.
  Özellikle "Kod daha önce tanımlanmış; eski kod tekrar kullanılamaz" hatası
  SYYDiagnosisTypeDefRules / SYYDiagnosisSliceDefRules kaynaklıydı.

Yapılan kod değişiklikleri:
  1. Üç Code alternatif anahtarı kaldırıldı; her birinde
     HasIndex(Code).IsUnique().HasFilter(PostgreSqlIndexFilters.NotDeleted) var.
  2. FK'ler sayısal kod yerine kalıcı GUID kimliğine taşındı:
       ProcedureDef.ProcedureTypeDefId -> ProcedureTypeDef.Id
       SYYDiagnosisDef.SYYDiagnosisTypeDefId -> SYYDiagnosisTypeDef.Id
       SYYDiagnosisDef.SYYDiagnosisSliceDefId -> SYYDiagnosisSliceDef.Id
     Eski ProcedureType/SYYDiagnosisType/Slice int kodları API/sorgu uyumu için
     bırakıldı. Create işlemleri koddan güncel aktif GUID çözümler; Update yalnız
     seçim değişmişse çözümler. Değişmeyen eski ilişki farklı kayda bağlanmaz.
  3. Üç tanımın unique sorguları yalnız !IsDeleted kayıtlarını sayar.
     Soft-delete edilmiş alt çocuklar üst kaydın soft-delete edilmesini engellemez;
     silinmemiş çocukların FK koruması devam eder. Aktif çocuk varsa pasifleştirme
     kontrolleri GUID üzerinden yapılır.
  4. Kalan tanım modüllerinin Code unique indeksleri ve QueryHandler/Rules
     dizini denetlendi; standart Code kontrolleri zaten !IsDeleted idi.
     Kimlik/token/path benzersizliği değiştirilmeyip güvenlik korunmuştur.

GÜNCEL VERİTABANI DURUMU (28.10.2026):
  Kullanıcı ilk migration'ı yerelde yeniden oluşturdu; eski şemayı dönüştüren
  MigrationSupport yardımcıları ve SQL scriptleri artık kullanılmıyor.
  Yereldeki yeni InitialCreate'nin Guid FK / IsDeleted=false unique indeksleri

Kabul senaryoları:

  - Eski soft-delete kaydın Id/audit tarihi korunur.
  - İlişkili geçmiş tetkik/tanı eski Guid ID'ye bağlı kalır, yeni X'e geçmez.
  - Aktif ilişkisi olan üst tanım silme/pasifleştirme koruması devam eder.
  - Code dışında UserName/TokenHash gibi alanların politikası değişmez.
  - Yeni metadata regresyonu: dotnet run --project KLMN/Tests/SoftDeletedCodeReuse.Regression

3. ORTAK ENTITY KURALLARI — ÖZELLİKLE KORU
-----------------------------------------
BaseEntity zaten şunları taşır:
  Guid Id,
  DateTime CreatedDate,
  Guid? CreatedBy,
  DateTime? UpdatedDate,
  Guid? UpdatedBy,
  bool IsActive,
  bool IsDeleted,
  DateTime? DeletedDate,
  Guid? DeletedBy,
  uint Version.

- Version = PostgreSQL xmin (EF Core/Npgsql IsRowVersion); AYRI bir normal
  Version kolonu oluşturma. Update / status / delete istekleri güncel
  Version ister; eşzamanlı değişiklikte 409 dönmelidir.

  alanlarını doldurur. Delete fiziksel silme değil soft delete'dir.
- Global EF query filter aktiflik + silinmişlik durumunu kapsar;
  pasif kayıtları listeleyen sorgularda gerektiğinde IgnoreQueryFilters()
  ve açık IsDeleted filtresi kullanılır.
- Tüm tarihleri PostgreSQL'de UTC tut; Angular datetime-local
  dönüşümlerinde ValidityPeriodUtils'ı kullan.
- Tanım geçerlilik tarihi gerekiyorsa entity'yi EffectiveDatedEntity'den
  türet. EffectiveDatedEntity : BaseEntity; nullable DateTime? ValidFrom
  (dahil) ve ValidTo (hariç) içerir. Null = o tarafta tarih sınırı yok.
  Her iki tarih girilirse başlangıç bitişten önce olmalıdır.
- Tarih kullanılan EF konfigürasyonunda
  EffectiveDatedEntityConfiguration<TEntity> kullan. ValidFrom/ValidTo
  property'lerini entity içerisinde veya konfigürasyonlarını ayrı
  ayrı TEKRAR TANIMLAMA.
- Bu standart şimdilik ForcesCommandDef, MilitaryUnitDef ve
  PurchaseNumberDef, CityDef, MilitarySchoolDef ve MilitaryClassDef üzerinde geçerlidir.
